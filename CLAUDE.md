## Commands

```bash
npm run start:dev          # watch mode (nest start --watch)
npm run start:prod         # node dist/main (requires npm run build first)
npm run build              # nest build -> dist/
npm run lint               # eslint --fix over src, apps, libs, test
npm run format             # prettier --write over src and test

npm test                   # jest unit tests (rootDir: src, testRegex: *.spec.ts)
npm test -- src/app.controller.spec.ts   # single file
npm test -- -t "should return"           # single test by name
npm run test:cov           # coverage -> ./coverage
npm run test:e2e           # jest --config ./test/jest-e2e.json (*.e2e-spec.ts under test/)
```

Docker: `docker compose -f docker-compose.sqlite.yml up --build` (or `docker-compose.postgresql.yml`).

Both `package-lock.json` and `pnpm-lock.yaml` are committed. `pnpm-workspace.yaml` exists solely to allow native build scripts for `@swc/core` and `better-sqlite3` under pnpm — if you install with pnpm and get a missing-binding error from `better-sqlite3`, that file is the reason it works at all.

## Environment

Copy `sample.env` to `.env`. `DB_TYPE` is one of `sqlite` | `postgres` | `mysql`; `DB_HOST`/`DB_PORT`/`DB_USERNAME`/`DB_PASSWORD`/`DB_NAME` are only read by the postgres and mysql factories. The sqlite factory hardcodes `./database.sqlite` and ignores `DB_NAME` (the config lookup is commented out in [database.sqllite.ts](src/infra/database/factory/database.sqllite.ts)). All factories run with `synchronize: true` — there are no migrations; schema comes from the TypeORM entities.

`SWAGGER_ENABLED` (default on; set to `false` to not mount the docs) and `SWAGGER_PATH` (default `docs`) control the OpenAPI UI.

## API documentation

Swagger UI is served at `http://localhost:3000/docs`, the raw OpenAPI document at `/docs/json`. Setup lives in `setupSwagger()` in [main.ts](src/main.ts).

Schemas are generated by the **`@nestjs/swagger` CLI plugin**, configured in [nest-cli.json](nest-cli.json) — that is why the request/response models need no `@ApiProperty`. Two consequences:

- `dtoFileNameSuffix` is restricted to `.request.ts` and `.response.ts`, deliberately excluding the `.dto.ts` files under `@application/interfaces`. The application layer stays free of OpenAPI concerns; only HTTP models are introspected. A new HTTP model must use one of those two suffixes or its schema comes out empty.
- The plugin only runs through the Nest CLI (`nest build` / `nest start`). Compiling with bare `tsc` produces a document with no property schemas.

Route documentation uses the helpers in [src/interfaces/http/swagger/](src/interfaces/http/swagger/) rather than plain `@ApiResponse`, because a naive `@ApiResponse({ status: 404 })` would be a lie here: controllers never throw and never set the transport status, so Nest always sends 200 (201 on POST) and the real outcome is the `code` field in the `CoreResponse` body.

- `ApiCoreResponse(model, { httpStatus, successCode, isArray, description, codes })` declares the one status the route really emits, wraps `model` in the `CoreResponseSchema` envelope via `allOf`, and renders `codes` as the list of body `code` values the route can return. Pass `Boolean`/`String`/`Number` as `model` for a primitive payload.
- `ApiInvalidIdResponse()` documents the single genuine HTTP 400: `ParseIntPipe` rejecting a non-numeric `:id` before the handler runs, which returns Nest's standard error shape, not a `CoreResponse`. Add it to every route with an `:id` param.
- `CoreResponseSchema` mirrors `CoreResponse` for the generator. `CoreResponse` itself stays decorator-free — it is a `@shared` primitive, and documenting HTTP belongs to the delivery layer.

The `codes` lists are per-route because the controllers are not consistent with each other: `POST /user` sets `code: 201` while `POST /product` leaves it at the default 200, and product routes report repository failures as 400 where user routes use 500. Read the handler before documenting a new one.

## Architecture

Clean Architecture with four layers and TS path aliases (defined in [tsconfig.json](tsconfig.json)) that make the dependency direction explicit. **Always import across layers via the alias, never by relative path.**

| Alias | Layer | May depend on |
| --- | --- | --- |
| `@domain/*` | entities, repository *interfaces*, `Result` | nothing |
| `@application/*` | use cases + their input/output DTOs | `@domain` |
| `@infra/*` | TypeORM entities, repository impls, DB factories | `@domain` |
| `@interfaces/*` | controllers, HTTP request/response models, Nest modules | all of the above |
| `@shared/*` | `CoreResponse`, Winston logger | `@domain` |

### The three-model chain

Every field crosses three separate class shapes, converted with `plainToInstance` at each boundary. This duplication is deliberate — don't collapse it:

```
HTTP body   -> CreateUserRequestModel      (@interfaces/http/dto/requests/user)
            -> CreateUserUseCaseInput      (@application/interfaces/user)  [@Expose]
            -> User (domain entity)        (@domain/entities)              [@Expose]
            -> UserTypeOrmEntity           (@infra/persistence/typeorm/entities)
back out    -> GetUserUseCaseOutput -> GetUserOutputResponseModel
```

Repository impls call `plainToInstance(Domain, row, { excludeExtraneousValues: true })`, so a domain field without `@Expose()` silently drops out of every response. That is the single most common cause of "the field disappeared".

### Result and CoreResponse

`Result<T>` ([result.ts](src/domain/core/result.ts)) is the error channel for domain, application, and infra — those layers never throw across a boundary and never know about HTTP. `error` is always `string[] | null`. `getValue()` throws on a failed result, so check `isSuccess` first. `ResultAsync(promise)` ([resultAsync.ts](src/domain/core/resultAsync.ts)) wraps a promise into a `Result`.

Controllers are the only place that maps `Result` to HTTP: they return `CoreResponse<T>` ([response.ts](src/shared/core/response.ts)) with an explicit numeric `code` and pick the status by substring-matching the error strings (`'not found'` → 404, `'already exists'` → 409). Nest itself always sends 200/201 — the real status lives in the JSON body's `code`. There is no exception filter and no global `ValidationPipe`; request models carry no `class-validator` decorators, so bodies are unvalidated by design in this template.

Note that `GetUserUseCase.execute(id = 0)` returns `Result<GetUserUseCaseOutput[]>` for both list and by-id (by-id wraps the single result in an array); `id === 0` means "all".

### Wiring

Use cases are plain classes with constructor-injected repository *interfaces*, so they have no Nest decorators and must be registered with `useFactory` + `inject`. Repositories are bound to string tokens because an interface has no runtime identity:

```ts
{ provide: 'UserRepository', useClass: UserRepository },
{ provide: CreateUserUseCase,
  useFactory: (repo: UserRepository) => new CreateUserUseCase(repo),
  inject: ['UserRepository'] },
```

Feature modules live in [src/interfaces/http/modules/](src/interfaces/http/modules/), each importing `DatabaseModule` + `TypeOrmModule.forFeature([...])`. A module must `exports` anything another module composes with — `UserModule` exports `GetUserUseCase` so `ProductModule` can build `UserProductUseCase` from it (see [product.module.ts](src/interfaces/http/modules/product.module.ts)).

`DatabaseModule` ([database.module.ts](src/infra/database/database.module.ts)) reads `DB_TYPE` and delegates to `DatabaseFactory` ([database.config.factory.ts](src/infra/database/database.config.factory.ts)), which returns `TypeOrmModuleOptions` from one of the three classes in [factory/](src/infra/database/factory/). **Each factory hardcodes its own `entities: [...]` array — a new TypeORM entity must be added to all three files** or it will exist under sqlite and vanish under postgres/mysql.

### Adding a resource

1. Domain entity (`@Expose()` on every exposed field) + repository interface returning `Promise<Result<...>>`.
2. TypeORM entity, registered in all three DB factories.
3. Repository impl with `@InjectRepository`, catching errors into `Result.fail`.
4. Use-case input/output DTOs, then use-case classes taking the interface.
5. Request/response models (files must end in `.request.ts` / `.response.ts`) + controller mapping `Result` → `CoreResponse`, annotated with `@ApiTags` and `ApiCoreResponse`.
6. Feature module with the `useFactory` providers; import it in [app.module.ts](src/app.module.ts).

Each DTO folder has an `index.ts` barrel that re-exports both named and default — add new DTOs there, since imports go through the barrel.

## Gotchas

- **Jest has no `moduleNameMapper` for the path aliases** (neither the `jest` block in `package.json` nor [test/jest-e2e.json](test/jest-e2e.json)). Any spec importing `@domain/...` etc. will fail to resolve until a mapper is added; the existing spec uses relative imports only.
- `tsconfig.json` sets `noImplicitAny: false` and `strictBindCallApply: false`, but `strictNullChecks: true` — repository methods legitimately return `Result<T | null>` and must be null-checked.
- Logging goes through `AppLogger` ([logger.service.ts](src/shared/logger/logger.service.ts)), installed in [main.ts](src/main.ts) with `bufferLogs: true`. Winston writes daily-rotated files to `logs/` and adds a custom `fatal` level.
- [mailer.service.ts](src/infra/services/mailer.service.ts) is an empty placeholder.
- `.github/workflows/update-clone-stats.yml` rewrites the clone badge in README.md on a schedule; the frequent "Update clone stats" commits on `main` come from it, not from development.
